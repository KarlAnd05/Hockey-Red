# Full site audit — 2 November 2026

Every feature tested end to end against a clean database: all four automated gates,
plus ~270 further checks driven through the real API and the real browser.

**Headline:** the site is structurally sound. Nothing is broken in the store engine,
the admin area, the permissions model or the statistics. Six real defects, three of
which sit on the one payment path that currently works. Most of what is missing is
content and configuration, not code.

## Defects

### 1. A guest cannot see the order they just placed — HIGH

Place an order by e-Transfer without signing in, then press **"View your order"**:

> **COULD NOT LOAD THAT ORDER** — Not your order.

The site tells the buyer that the order they placed thirty seconds ago isn't theirs.

**Cause.** `canAccessOrder()` in [server/routes/orders.js:14](server/routes/orders.js:14)
lets a guest in only when `?session=` matches the order's `stripe_session_id`. An
e-Transfer order has no Stripe session, so that test can never pass.

**What it breaks for every guest order:**

| | |
|---|---|
| `GET /api/orders/:id` | 404 |
| `GET /api/checkout/status/:id` | 403 |
| `GET /api/orders/:id/invoice` | 404 |

Signed-in buyers are completely unaffected — I verified all eight steps of that path.
But e-Transfer is the only payment method that works today, and most buyers won't
make an account first.

**Fix.** Issue a one-time access token with the e-Transfer checkout response and accept
it in `canAccessOrder`, the same shape as the chat thread token already in the codebase.

### 2. The buyer's basket is never emptied — HIGH (same flow)

After the federation marks a guest's transfer received, the goods they have already
paid for are still sitting in their basket, inviting them to buy again. The cart badge
still read **1** in my test.

**Cause.** [server/routes/admin.js:488](server/routes/admin.js:488) calls
`markOrderPaid(id)` with no `cartId`. The fallback clears "the signed-in buyer's newest
cart" — a guest has none. The `orders` table has no `cart_id` column, so the cart the
order was built from is never recorded.

**Fix.** Record `cart_id` on the order at creation and pass it to `markOrderPaid`.
The existing comment at [server/lib/orders.js:139](server/lib/orders.js:139) already
calls the fallback a guess.

### 3. The jersey size guide doesn't match the sizes you can buy — HIGH

This one is mine, from the size-guide work, and it is the one place where an error
costs the buyer money: the jersey is made to order and **all sales are final**.

| | |
|---|---|
| Sizes you can buy | XS, S, M, L, XL, XXL |
| Youth table | Small, Medium, Large, X-Large, Goalie |
| Adult table | Small, Medium, Large, X-Large, XX-Large, XXL Goalie |

Four separate problems:

- **XS is buyable and appears in neither table.** No measurements at all.
- **Youth sizes cannot be bought.** The chart advertises a full youth range and the
  buy button offers none. A parent cannot order for a child.
- **Goalie cuts cannot be bought** although they are charted.
- **S/M/L/XL are ambiguous.** A parent who measures a child against the Youth table and
  picks "L" receives an Adult Large: **27-inch chest against the 21 inches they
  measured.**

**Fix.** Either rename the variants to match the chart (Youth S–XL, Adult S–XXL,
Goalie) or cut the youth and goalie columns and drop XS. The first is better — the
federation runs a youth programme.

### 4. The jersey chart shows on garments that are not jerseys — MEDIUM

`hasSizes` in [assets/store.js:526](assets/store.js:526) matches any XS–XXL variant, so
the jacket, t-shirt, crewneck and polo all display the jersey spec sheet and the words
*"These are made-to-order jerseys."* A t-shirt buyer is given jersey measurements.
Caps and pucks correctly show nothing. Also mine.

### 5. Five admin sidebar links read the word "undefined" — MEDIUM

```html
<svg viewBox="0 0 24 24" aria-hidden="true">undefined</svg>
```

The sidebar reads **"undefined Messages"**, **"undefined Sponsors"**,
**"undefined Schedule"**, **"undefined Teams"**, **"undefined Game sheets"**.

**Cause.** `ICONS` in [scripts/build-admin-pages.mjs:12](scripts/build-admin-pages.mjs:12)
defines 13 keys; the nav asks for 18. The five newest admin modules were added to the
nav and never to the icon map, so `ICONS[icon]` is `undefined` and gets interpolated
into the SVG, where the browser renders it as visible text.

This is very likely why you couldn't find the game-sheet page, and why the menu felt
broken. **Fix:** add the five missing icons.

### 6. The wordmark collides with the Sign In button on phones — MEDIUM

| Width | Overlap |
|---|---|
| 480px | none |
| 414px | none |
| **375px** | **8px** |
| **360px** | **12px** |

375px is the iPhone SE/mini/12/13/14; 360px is most Android phones. The "Y" of
"HOCKEY" sits underneath the Sign In button on **every page**. The wordmark is
`white-space: nowrap; overflow: visible; text-overflow: clip`, so it spills instead of
truncating. No horizontal page scroll — purely the header.

### 7. Sponsor website links accept garbage — LOW

| Entered | Stored and published |
|---|---|
| `javascript:alert(1)` | `https://javascript:alert(1)` |
| `data:text/html,<script>…` | `https://data:text/html,<script>…` |
| `//evil.example.com` | `https:////evil.example.com` |

**Not an XSS** — the `https://` prefix leaves an unparseable URL that no browser will
execute. But it publishes dead links on a page every visitor sees, and the
protocol-relative case quietly becomes an off-site link.

[server/routes/programs.js:83](server/routes/programs.js:83) handles the identical field
correctly by rejecting to `''`. [server/routes/sponsors.js:37](server/routes/sponsors.js:37)
should do the same.

### 8. The catch-all shipping zone can be set to zero, silently — LOW

Create a zone with no rate, make it the catch-all, and **every unmapped country ships
free.** Nothing warns you. I hit this by accident mid-audit, then reproduced it
deliberately and restored the correct zone. It is the same class of bug that was fixed
in the pricing code, now reachable through the admin UI instead.

**Fix.** Refuse to make a zone the catch-all unless it has a non-zero rate.

### 9. e-Transfer emails are logged without a label — LOW

Every other notification sets `kind`. `sendEtransferInstructions`
([server/lib/notifications.js:430](server/lib/notifications.js:430)) doesn't, leaving 9
unlabelled rows in `email_log`. It is the single most important email in the payment
flow you are actually using, and it's the one you can't filter for.

### 10. Two different payment addresses — LOW

The store's e-Transfer address comes from `ETRANSFER_EMAIL`. Membership payments point
at **`support@lebanonhockey.com`, hardcoded** in three places in
[server/routes/membership.js](server/routes/membership.js) and once in
`notifications.js`. Change the configured address and membership still points elsewhere.

### 11. `ETRANSFER_EMAIL` is undocumented — LOW

It is absent from `.env.example`, yet it is the switch that turns on the only working
payment method. Deploy from the example file and the store has no way to take money,
with nothing to say why.

### 12. No link previews on the main pages — LOW

The news, team and player pages are server-rendered and carry Open Graph tags. The 22
static pages — **home, membership, donation, store** — carry none. Those are exactly
the pages shared on WhatsApp, and they currently preview as a bare URL. No `og:image`
renders anywhere yet because there are no photos; once a photo is set it appears
correctly (verified).

### 13. Smaller things

- No `/robots.txt`, no `/sitemap.xml`.
- **No scheduled publishing.** `published_at` only sorts; a post dated 2099 goes live
  immediately.
- `npm run build` marks 31 files modified on Windows with **no content change** — no
  `.gitattributes` with `core.autocrlf=true`. Makes real changes easy to miss.
- One finalised game in the live database has **zero players on its sheet**.
- **Contact** and **Donate** are reachable only from the footer, never the main nav —
  on a site whose purposes are recruitment and fundraising.

## Not broken — waiting on content or configuration

Nothing here is a code fault. All of it stops the site being useful.

### Blocking launch

- **The server will not start in production.** `NODE_ENV=production` throws
  `SESSION_SECRET must be set in production`. 17 of the `.env.example` keys are unset.
- **Donations cannot be taken at all.** The button reads *"Donations unavailable"* and
  is disabled. Unlike the store, donations have **no e-Transfer fallback** — there is
  no way to give the federation money through this page today.
- **Card payments are off** everywhere (no `STRIPE_SECRET_KEY`).
- **No email is actually sent.** Without SMTP every message is written to the log and
  dropped. Routing is correct — admin mail never reaches the buyer, reset mail only
  ever goes to the account holder (verified across 30 messages).
